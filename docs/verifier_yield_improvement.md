# Verifier yield improvement plan

Started: 2026-08-02 00:45 +08:00

Goal: recover NOP/Oracle validator yield to at least 40–50% while reducing
timeouts and slow dependency downloads. Change one variable at a time and
observe production results for at least 15 minutes before accepting, reverting,
or moving to the next experiment.

## Measurement rules

- Primary metric: `validate` stage successes divided by all terminal validate
  outcomes (`succeeded + failed + rejected`) in PostgreSQL.
- Report 15, 30, 60, and 120 minute windows.
- Secondary metrics: remote farm success/failed/timeout counts, p50 duration,
  exact-600-second server timeouts, and failure classes.
- Do not count deterministic NOP/Oracle reward mismatches as proxy/cache
  failures. Track infrastructure/build failures separately.
- Do not change two routing/cache variables in the same observation window.

## ATS/cache facts to preserve

- `npm config set strict-ssl false` disables npm's validation of an HTTPS
  certificate. It does not cause ATS to decrypt an HTTPS CONNECT tunnel.
- ATS can cache requests whose client-facing URL is plain HTTP, including an
  explicit internal HTTP reverse-proxy registry endpoint.
- The current npm endpoint is `https://registry.npmmirror.com/`, so forward
  proxy requests are CONNECT tunnels and are not cacheable by ATS.
- ATS currently has a 200 GiB disk cache enabled, but its parent rules are
  limited to `scheme=http`; HTTPS CONNECT traffic does not match those rules.
- A cacheable npm design therefore requires either an explicit internal HTTP
  reverse-proxy/remap endpoint or a native npm cache such as Verdaccio. TLS
  interception is not required for the explicit reverse-proxy design.

### 3. ATS HTTP npm reverse proxy — completed, failed and reverted

Attempted at 2026-08-02 01:52–01:56 +08:00:

- added a temporary listener on `7.244.3.78:3131`;
- remapped its plain-HTTP client URL to
  `https://registry.npmmirror.com/`;
- enabled normal HTTP caching, relaxed the required cache headers for this
  route, and allowed three internal redirects so ATS could follow the npm
  registry's redirect to `cdn.npmmirror.com`;
- no production or pilot worker was pointed at the endpoint before its smoke
  test passed.

Pre-deployment observations:

- plain `http://registry.npmmirror.com/...` is not a usable cache path because
  the origin returns an immediate 301 to HTTPS;
- npm metadata for `material-design-icons@3.0.1` points to an HTTPS registry
  tarball URL;
- that registry tarball URL returns a 302 to a 32,990,579-byte CDN object with
  a one-day public cache lifetime;
- the exact CDN object downloaded successfully from this node through SG, HK,
  and DE in two attempts each, although the earlier broader DE smoke set still
  makes DE unsafe for general routing.

Result:

- both reverse-proxy tarball smoke requests returned ATS
  `502 Next Hop Connection Failed` after about 60 seconds;
- the ATS hierarchy log showed the remapped HTTPS origin connection going
  directly to parent IP `172.18.102.38` instead of issuing an HTTP CONNECT
  tunnel through that parent;
- the corporate parent expects forward-proxy CONNECT, not an origin TLS
  session, so ATS cannot use this simple reverse-map design with the available
  parent path;
- the endpoint was never used by BuildKit and is being removed.

Verdict: ATS can cache the public npm payload only after it sees decrypted HTTP,
but the present corporate-parent topology prevents this simple reverse proxy
from reaching an HTTPS origin. `strict-ssl=false` changes npm certificate
validation only and does not decrypt a CONNECT tunnel for ATS. Use a
protocol-native cache such as Verdaccio for the next controlled experiment;
Verdaccio can fetch through a normal HTTP proxy and rewrite npm tarball URLs
back to itself.

Next debugging ideas:

1. Deploy a single-node Verdaccio pilot on `7.244.3.78`, backed by persistent
   `/data` storage and upstreamed to npmmirror through the healthy proxy path.
2. Confirm the remote farm can install `material-design-icons@3.0.1` twice from
   Verdaccio, verify identical integrity, and measure a warm-cache hit.
3. Only then rewrite `runbox/runbox7` remote build args/Dockerfile to use the
   pilot registry and observe a new 15-minute controlled window.
